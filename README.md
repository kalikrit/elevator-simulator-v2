# Elevator Simulator v2

🔗 **Live demo:** https://kalikrit.github.io/elevator-simulator-v2/

[![Deploy to GitHub Pages](https://github.com/kalikrit/elevator-simulator-v2/actions/workflows/deploy.yml/badge.svg)](https://github.com/kalikrit/elevator-simulator-v2/actions/workflows/deploy.yml)

Симулятор работы 4 лифтов в 25-этажном доме с двумя алгоритмами управления и сравнением их эффективности.

## Что это

Учебный проект, в котором я переписал [первую версию](https://github.com/kalikrit/elevator-simulator) с нуля, применив принципы проектирования: SOLID, DIP, KISS, YAGNI, DRY. Основная цель — не «сделать приложение», а **пройти правильный процесс**: требования → модель → контракты → тесты → реализация → UI.

## Что делает

- Симулирует 4 лифта в 25-этажном доме.
- Поддерживает 2 алгоритма выбора лифта: «Ближайший доступный» и «Прогнозирующий по полному времени».
- Воспроизводит фиксированный сценарий «Час-пик» (15 вызовов за 16 секунд: 1 вызов вверх с 1 этажа + 14 спусков).
- Задействует все 4 лифта, выявляет статистически значимую разницу между алгоритмами.
- Собирает метрики: общее время, среднее/макс. ожидание, пробег, остановки, количество вызовов.
- Позволяет сравнить два алгоритма на одном сценарии.
- Визуализирует движение лифтов в реальном времени.
- Поддерживает ручные вызовы лифта кнопкой на этаже.

## Стек

- **Vue 3** + `<script setup>` + **TypeScript**
- **Vite** — сборка
- **Vitest** — тесты
- **SCSS** — стили
- Без backend, всё в браузере

## Архитектура

Три слоя с односторонними зависимостями:

```
components/  ← UI, тупые компоненты
    │
    ▼
composables/ ← мост между доменом и Vue (реактивность, время)
    │
    ▼
domain/      ← чистая логика, ноль зависимостей от Vue
```

**Правило проверки:** в `domain/` не должно быть импортов из `vue`, `performance`, `setTimeout`, `window`. Если есть — граница сломана.

### Домен

| Модуль | Ответственность |
|---|---|
| `types.ts` | Словарь предметной области |
| `config.ts` | Конфигурация мира по умолчанию |
| `queue.ts` | Работа с очередью лифта (SCAN-подобная сортировка) |
| `selector.ts` | Алгоритмы выбора лифта (стратегии) |
| `metrics.ts` | Сбор и агрегация метрик |
| `algorithms.ts` | Реестр алгоритмов с описаниями |
| `scenarios.ts` | Сценарии как данные |
| `elevatorSystem.ts` | Ядро: состояние + tick + requestTrip |

### Composables

- `useElevatorSystem` — реактивность + fixed timestep + виртуальные часы
- `useScenarioRunner` — запуск сценария по виртуальному времени, проверка завершения

### UI

- `ElevatorSimulator.vue` — корневой компонент, хранит историю метрик по алгоритмам
- `Floor.vue` / `Floors.vue` — этажи и шахты
- `ControlsPanel.vue` — селект алгоритма, кнопки запуска/сброса
- `AlgorithmDescription.vue` — раскрываемое описание выбранного алгоритма
- `MetricsPanel.vue` — метрики одного запуска
- `MetricsComparison.vue` — таблица сравнения двух алгоритмов

## Сравнение алгоритмов

На сценарии «Час-пик» (15 вызовов, все 4 лифта) алгоритмы показывают **классический trade-off** между пропускной способностью и справедливостью:

| Метрика | Ближайший доступный | Прогнозирующий по полному времени |
|---|---|---|
| Общее время | 78.11 с | **70.59 с** |
| Среднее ожидание | **17.63 с** | 21.33 с |
| Макс. ожидание | 53.10 с | **45.58 с** |
| Пробег | **176 эт.** | 182 эт. |
| Остановки | 22 | 22 |

**Вывод:**

- `nearest` — эгоистичный: обслуживает каждый вызов «как только может». Среднее ожидание ниже, но отдельные пассажиры ждут долго.
- `totalTime` — социальный: оптимизирует общее время системы. Максимум ожидания ниже, но средний пассажир ждёт дольше — алгоритм жертвует новыми вызовами ради уже принятых.

Это **реальный trade-off**, а не баг. Настоящие системы (Otis Compass, Schindler PORT) используют гибридные подходы с весами и приоритетами, чтобы балансировать оба критерия.

### Детерминированность

Метрики воспроизводимы: один сценарий + один алгоритм = идентичные цифры на любом устройстве. Это достигается через **fixed timestep** (16 мс) и виртуальные часы симуляции — независимо от частоты кадров браузера.

## Тесты

56 тестов на домен (`npm run test:run`). Composables и UI не покрыты unit-тестами осознанно: они тонкие, а тестирование `requestAnimationFrame` и `performance.now()` требует фейковых таймеров и jsdom. Вместо этого — smoke-тесты в браузере.

Покрытие по модулям:

- `queue` — 16
- `selector` — 11
- `metrics` — 10
- `elevatorSystem` — 16
- `scenarios` — 4

## Процесс разработки

Проект писался по шагам:

1. Требования и use cases
2. Модель предметной области
3. Границы модулей
4. Контракты (сигнатуры без реализации)
5. Scaffold проекта + репозиторий
6. Домен: `queue` → `selector` → `metrics` → `elevatorSystem` (TDD: тесты → реализация → коммит)
7. Composables + smoke-тест
8. UI-компоненты + техно-стиль
9. Детерминированные метрики (fixed timestep)
10. Плотный сценарий «Час-пик»

Каждый модуль домена покрыт тестами **до** реализации (красная фаза TDD). Это дало свободу рефакторить без страха сломать поведение.
